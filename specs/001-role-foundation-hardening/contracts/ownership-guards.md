# Contract: Ownership Guards (US1)

عقد سلوكي لأربع دوال middleware في `Backend/middlewares/ownership.js`. لا تغيير في
توقيع الاستدعاء (كلها middleware قياسي `(req, res, next) => void`، تعمل بعد `protect`
و`allowedTo`) — العقد هنا يصف **قرار القبول/الرفض**، لا الشكل البرمجي.

## المدخل المشترك للأربعة

- `req.user` — كائن مستخدم مُصادَق عليه بالفعل (بعد `protect`)، يحتوي `role` و `_id`.
- `req.params.id` أو `req.params.playerId` (حسب الحارس) — معرّف المورد المطلوب.
- المستند المطلوب موجود في قاعدة البيانات (حالة "غير موجود" تُعالَج قبل فحص الملكية —
  انظر قاعدة الترتيب أدناه).

## قاعدة الترتيب الثابتة (لا تتغير في هذه المرحلة)

1. المستند غير موجود ← 404، بصرف النظر عن رول الطالب.
2. المستند موجود ← يُفحَص الرول:
   - `admin` ← يمر دائماً (`next()` بلا فحص إضافي).
   - رول معروف آخر (`coach`/`observer` حسب الحارس) ← يُفحَص شرط الملكية الخاص به.
   - **أي رول آخر ← 403 من الفرع الافتراضي (جديد في هذه المرحلة).**

هذا الترتيب MUST NOT ينعكس أو يتغيّر لأي حارس — تغييره يعني تحويل 404 إلى 403 أو العكس
لسيناريوهات قائمة، وهو ما تمنعه FR-004 صراحة.

## 1. `checkPlayerOwnership`

**المورد**: `Player`، عبر `req.params.playerId ?? req.params.id`.

| الرول | القرار | الشرط |
|---|---|---|
| `admin` | يمر | — |
| `observer` | يمر | `req.user._id` ضمن مصفوفة `player.observers` |
| `observer` | 403 | غير ذلك |
| `coach` | يمر | `player.coach` (إن وُجد) يساوي `req.user._id` |
| `coach` | 403 | `player.coach` فارغ (لاعب يتيم) أو لا يساوي `req.user._id` |
| **أي رول آخر** | **403 (جديد)** | — بلا فحص لأي حقل في المستند |

**رسالة الرفض لكل الحالات (بما فيها الفرع الجديد)**: نفس النص القائم اليوم —
`"You are not allowed to access this player's data"`.

## 2. `checkReportOwnership`

**المورد**: `ScoutingReport`، عبر `req.params.id`، مُقارَن أيضاً بـ `req.params.playerId`.

| الرول | القرار | الشرط |
|---|---|---|
| `admin` | يمر | — |
| `coach` أو `observer` | يمر | `report.coach` يساوي `req.user._id` **و** `report.player` يساوي `req.params.playerId` |
| `coach` أو `observer` | 403 | أحد الشرطين غير متحقق (رسالتان مختلفتان قائمتان: عدم الملكية / عدم تطابق اللاعب) |
| **أي رول آخر** | **403 (جديد)** | — |

## 3. `checkMediaOwnership`

**المورد**: `PlayerMedia`، عبر `req.params.id`، مُقارَن أيضاً بـ `req.params.playerId`.

**⚠️ التغيير الأهم في هذا العقد** — القاعدة القائمة اليوم تفحص `uploadedBy` فقط بلا أي
اعتبار للرول. القاعدة الجديدة تضيف شرط الرول **كبوابة أولى**:

| الرول | القرار | الشرط |
|---|---|---|
| `admin` | يمر | — |
| `coach` أو `observer` | يمر | `media.uploadedBy` يساوي `req.user._id` **و** `media.player` يساوي `req.params.playerId` |
| `coach` أو `observer` | 403 | أحد الشرطين غير متحقق |
| **أي رول آخر** | **403 (جديد)** | — حتى لو كان `media.uploadedBy` يساوي `req.user._id` بالمصادفة |

**لماذا هذا التغيير لا يخالف FR-003 (بقاء رسالة/رمز الرفض)**: لا سيناريو قائم لرول
`coach`/`observer`/`admin` يتأثر — كلهم كانوا يمرّون بفحص `uploadedBy` وما زالوا. السيناريو
المتأثر (رول ثالث يمر بفحص `uploadedBy` وحده) لم يكن ممكناً تحقيقه أصلاً قبل هذه المرحلة
(لا رول رابع كان موجوداً)، فلا "سلوك قائم" يتغيّر — فقط ثغرة كانت ستُفتَح تلقائياً عند
إضافة أي رول لاحقاً تُغلَق الآن مسبقاً.

## 4. `checkSeasonMatchAttendee`

**المورد**: `SeasonMatch`، عبر `req.params.id`.

| الرول | القرار | الشرط |
|---|---|---|
| `admin` | يمر | — |
| `coach` أو `observer` | يمر | `req.user._id` ضمن مصفوفة `match.attendees` |
| `coach` أو `observer` | 403 | غير ذلك |
| **أي رول آخر** | **403 (جديد)** | — |

## معايير التحقق (يُختبَر آلياً — FR-020)

لكل حارس من الأربعة:

1. **إيجابي (admin)**: رول `admin` يمر لأي مستند من هذا النوع، بصرف النظر عن أي حقل
   ملكية فيه.
2. **إيجابي (الرول المالك)**: `coach`/`observer` يمرّان بالضبط بنفس الشروط الموثّقة
   أعلاه — **لا فرق عن السلوك قبل هذه المرحلة**.
3. **سلبي (الرول غير المالك)**: `coach`/`observer` يُرفَضان بنفس الرمز والرسالة
   القائمين حين لا يتحقق شرط الملكية — **لا فرق عن السلوك قبل هذه المرحلة**.
4. **سلبي (رول غير معروف) — الاختبار الجديد**: هوية مستخدم مُصطنعة في الذاكرة برول خارج
   المجموعة `{admin, coach, observer}` (مثلاً `'not-a-real-role'`) تُستدعى بها الدالة
   مباشرة (بلا مرور بقاعدة بيانات أو فاليديشن — طبقاً لقرار `research.md` §4) على مستند
   موجود، وأي قيمة حقول ملكية فيه (بما فيها قيم تتطابق بالمصادفة مع هوية الطالب) —
   والنتيجة MUST تكون رفضاً بـ 403 من `next(new AppError(...))`.
