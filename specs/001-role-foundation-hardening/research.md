# Phase 0 Research: Role Foundation Hardening

كل بند في `Technical Context` بقسم `plan.md` مُحدَّد مسبقاً من فحص الكود الفعلي — لا يوجد
`NEEDS CLARIFICATION` متبقٍّ هناك. هذا الملف يوثّق القرارات التقنية التي تحتاج تبريراً
قبل التنفيذ: أين يوضع كل تعديل، ولماذا بهذا الشكل بالذات دون غيره.

## 1. مكان تعريف ثابت الرولات (US3 / FR-011, FR-012)

**Decision**: ملف جديد `Backend/constants/roles.js` يُصدِّر:
- مصفوفة/تعداد بالقيم الثلاث القائمة (`admin`, `coach`, `observer`) بنفس الترتيب
  الموجود اليوم في `userModel.js:23`.
- `Backend/models/userModel.js` يستورد منه ويبنـي `enum` الحقل من هذه القيمة — لا يُكتب
  التعداد حرفياً في الموديل بعد الآن.

**Rationale**: الدستور (Principle VII) ينص صراحة: "الباك إند: ثابت مُصدَّر واحد MUST
يكون مصدر الحقيقة، و `userModel.js` (`role.enum`) يشتق منه — لا العكس". مجلد
`Backend/` ليس فيه `constants/` بعد؛ إنشاؤه بملف واحد أقل تكلفة معمارية من إضافة حزمة أو
config جديد، ومتّسق مع نمط الاستيراد المباشر السائد في المشروع (`utils/`, `services/`
كلها مجلدات مسطّحة بملفات مُصدَّرة).

**Alternatives considered**:
- **وضع الثابت داخل `utils/`**: مرفوض — `utils/` في هذا المشروع مخصص لأدوات ومنطق
  (validation, apiFeatures, mediaUrl)، لا لثوابت نطاق. الفصل يجعل البحث عن "أين تُعرَّف
  الرولات؟" مباشراً.
- **الإبقاء على التعداد في `userModel.js` وتصدير مرجع له**: مرفوض — الدستور يحدد اتجاه
  الاشتقاق صراحة (الموديل يشتق من الثابت، لا العكس)؛ عكسه ينتهك نص المبدأ حرفياً.

## 2. شكل الثابت: مصفوفة أم كائن تعداد؟

**Decision**: كائن تعداد شبيه بـ enum (`export const ROLES = { ADMIN: 'admin', COACH:
'coach', OBSERVER: 'observer' }`) بالإضافة إلى `export const ROLE_VALUES =
Object.values(ROLES)` للاستخدام في `mongoose.Schema` (`enum:`) وفي `express-validator`
(`.isIn(...)`).

**Rationale**: الاستخدامات القائمة في الكود نوعان: مقارنة مفردة (`req.user.role ===
"admin"`) واحتياج لقائمة قيم (`enum:`, `allowedTo(...roles)`, `.isIn()`). كائن التعداد
يخدم الحالة الأولى بقراءة أوضح (`ROLES.ADMIN` بدل `"admin"` حرفي، يُكتشف بالـ
autocomplete ويمنع أخطاء الطباعة)، والمصفوفة المشتقة تخدم الحالة الثانية بلا تكرار.

**Alternatives considered**:
- **مصفوفة فقط بلا كائن تسمية**: أبسط لكنها تُبقي الاستدعاءات على نصوص حرفية
  (`ROLE_VALUES.includes('admin')`) وتفقد فائدة الاكتشاف بالـ IDE التي هي بيت القصيد من
  المبدأ السابع.
- **TypeScript enum أو const assertion**: غير متاح — الباك إند JavaScript صرف (لا
  TypeScript)، والتحويل خارج نطاق هذه المرحلة تماماً.

## 3. تحويل حرّاس الملكية من fall-through إلى explicit deny (US1 / FR-001, FR-002)

**Decision**: كل حارس من الأربعة (`checkPlayerOwnership`, `checkReportOwnership`,
`checkMediaOwnership`, `checkSeasonMatchAttendee`) يُعاد كتابته بنمط موحّد:

```js
if (req.user.role === ROLES.ADMIN) return next();
if (req.user.role === ROLES.OBSERVER) { /* منطق الأوبزيرفر القائم */ return next()/reject; }
if (req.user.role === ROLES.COACH) { /* منطق الكوتش القائم */ return next()/reject; }
return next(new AppError("...", 403)); // default: deny — أي رول آخر
```

الرسالة والرمز في الفرع الافتراضي الجديد MUST تطابق رسالة الرفض القائمة لكل مورد
(`"You are not allowed to access this player's data"` وأخواتها) — الفرع الافتراضي رفض
جديد لرول غير قائم، لا رسالة جديدة يخترعها هذا التعديل.

**Rationale**: هذا تطبيق حرفي لـ FR-001 وللقيد C-2 في الدستور. الفارق الجوهري عن الكود
القائم: `checkPlayerOwnership` اليوم لا يفحص `coach` صراحة — يفترضه بعد استبعاد الاثنين
الآخرين. النمط الجديد يفحصه صراحة، فيتحول الرفض من نتيجة جانبية لفشل مقارنة (`player.coach
!== req.user._id` لرول لم يُقصَد أصلاً) إلى قرار مقصود.

**أهم قرار فرعي — `checkMediaOwnership` (FR-002)**: الحارس القائم يقارن `uploadedBy`
فقط بلا أي فحص للرول:
```js
if (media.uploadedBy.toString() !== req.user._id.toString()) { ... 403 ... }
```
هذا يعني أن أي رول جديد يرفع وسائط (لو مُنِح لاحقاً صلاحية الرفع) سيرى ما رفعه تلقائياً
دون قرار صريح. النمط الجديد MUST يضيف فحص رول **قبل** فحص `uploadedBy`، بحيث يكون:
`الرول ضمن (admin, coach, observer) AND uploadedBy === self` — تماماً كسلوك اليوم لهذين
الرولين، لكن رول ثالث غير هذين لا يمر أبداً مهما كانت قيمة `uploadedBy`.

**Alternatives considered**:
- **Lookup table (خريطة رول → دالة تحقق)** بدل `if/else` متسلسل: مرفوض لهذه المرحلة —
  أربعة حرّاس بمنطق مختلف جوهرياً لكل رول (الأوبزيرفر يفحص مصفوفة، الكوتش يفحص حقل
  مفرد)؛ تجريدها في جدول دوال يضيف طبقة غير ضرورية لأربع دوال فقط، ويخالف مبدأ "لا تصميم
  لاحتياجات افتراضية" — لو دور خامس أضاف تعقيداً حقيقياً مستقبلاً، ذلك وقتها.
- **حراسة عامة واحدة تُمرَّر لها خريطة الأدوار كوسيط**: مرفوض لنفس السبب، وأيضاً لأنه
  يعيد كتابة توقيع الدوال الأربعة المُستدعاة من ملفات routes متعددة — تغيير أوسع من
  اللازم لهدف "رفض صريح".

## 4. اختبار الفرع الافتراضي (US1 / FR-020 — القرار من `/speckit-clarify` Q2)

**Decision**: ملف اختبار جديد `Backend/tests/ownership.test.js` يستورد دوال الحرّاس
الأربعة مباشرة ويستدعيها بكائنات `req`/`res`/`next` مُصطنعة في الذاكرة —
`req.user = { _id: ..., role: 'not-a-real-role' }` — دون المرور بـ `User.create()` أو أي
طبقة فاليديشن أو قاعدة بيانات. يُتحقَّق أن `next` استُدعيت بـ `AppError` ذي `statusCode
=== 403`.

**Rationale**: هذا القرار محسوم بالفعل في `/speckit-clarify` (Option A). الطبقة الجديدة
في US3 (تحقق الفاليديشن من قيمة `role`) تمنع عملياً وجود مستخدم حقيقي في قاعدة البيانات
برول غير صالح، فاختبار عبر الشبكة (`supertest` على مستخدم حقيقي) يصبح مستحيلاً بنيوياً.
اختبار الوحدة المباشر يتحقق من الفرع نفسه بمعزل عن هذا القيد، وهو الأسرع والأقل اعتماداً
على حالة النظام.

**Alternatives considered**: موثّقة بالفعل في `spec.md` (قسم Question 2) — Option B
(تجاوز الفاليديشن في الإعداد) رُفض لأنه يعتمد على تجاوز صريح لطبقة أمان حقيقية داخل
الاختبار؛ Option C (رول اختباري في التعداد) رُفض لمخالفته المبدأ السابع مباشرة.

## 5. تعريف واحد لاشتقاق وجهة الرول (US2 / FR-007, FR-009)

**Decision**: خدمة Angular جديدة `frontend/src/app/core/services/role-landing.service.ts`
تُصدِّر دالة واحدة `landingFor(role: UserRole | undefined): string[]` (تُرجع مصفوفة
مسار مناسبة لـ `Router.createUrlTree`). المنطق:

```ts
switch (role) {
  case 'admin': return ['/dashboard/admin'];
  case 'observer': return ['/dashboard/observer'];
  case 'coach': return ['/dashboard/coach'];
  default: return ['/unauthorized'];
}
```

`role.guard.ts` و `dashboard.routes.ts` (فرع `path: ''`) يستدعيان هذه الخدمة بدل
تكرار سلسلة `? :` الثلاثية محلياً.

**Rationale**: القيد الدستوري صريح (Principle VII): "منطق تحديد الوجهة حسب الرول MUST
يُعرَّف مرة واحدة. التكرار الحالي بين `role.guard.ts` و `dashboard.routes.ts` MUST
يُوحَّد". `switch` بدل السلسلة الثلاثية المتداخلة القائمة لأن إضافة رول خامس مستقبلاً
تعني سطراً واحداً واضحاً بدل تعديل تعبير متداخل.

الموضع الثالث المذكور في وصف المرحلة (`signup.component.ts:113`) **لا يُلمَس** — تأكد
الفحص في `spec.md` (قسم Assumptions) أنه كود ميت: لا مسار `signup` في
`auth.routes.ts`، والتسجيل معطّل في الباك إند عمداً (`authRouter.js` لا يُحمِّل راوت
signup). لمسه يوسّع نطاق هذه المرحلة بلا داعٍ ويخالف "لا تصميم لاحتياجات لا وجود لها".

**Alternatives considered**:
- **دالة حرة مُصدَّرة بدل خدمة قابلة للحقن (`@Injectable`)**: مرفوض — كل منطق مشابه في
  `core/services/` (breadcrumb-context, player-context, query-builder) خدمات قابلة
  للحقن؛ دالة حرة هنا تكسر النمط القائم بلا مبرر، وتُصعّب استبدالها لاحقاً باختبار وهمي.
- **وضع المنطق داخل `AuthService` نفسها**: مرفوض — `AuthService` تدير الحالة (الجلسة،
  التوكن)؛ اشتقاق الوجهة منطق عرض/توجيه منفصل عن مسؤوليتها، وخلطه فيها يوسّع مسؤوليات
  خدمة موجودة مقابل خدمة جديدة صغيرة ومركّزة.

## 6. صفحة "غير مصرّح" — الموضع والبنية (US2 / FR-005, FR-006, FR-008)

**Decision**: مكوّن standalone جديد `features/unauthorized/unauthorized.component.ts`،
مُحمَّل عبر `loadComponent` في `app.routes.ts` على المستوى الجذري (**خارج** `path: ''`
المحروس بـ `authGuard` والمُغلَّف بـ `ShellComponent`)، بجانب `path: 'auth'`. يعرض نصاً
مترجَماً (`ngx-translate`) وزر تسجيل خروج يستدعي `AuthService` مباشرة.

**Rationale**: بناء الـ `Sidebar`/`Shell` يعتمد على معرفة رول صالح لإظهار العناصر
الصحيحة (كما هو موثّق في القيد C-1 وفي مصدر `sidebar.component.ts` المفحوص سابقاً في هذا
المشروع) — وهذا بالضبط الشرط المفقود عند رول غير معروف. عرض الصفحة خارج الهيكل الرئيسي
يتفادى إعادة استخدام مكوّن مبني على افتراض لا يتحقق هنا.

**Alternatives considered**:
- **صفحة داخل الـ shell القائم**: مرفوض — الـ shell نفسه (سايدبار مبني على رول) هو
  مصدر المشكلة الأصلية؛ عرضه لرول غير معروف قد يُنتج حالة جزئية غير محددة (سايدبار
  فارغ/معطوب) بدل صفحة نظيفة ونهائية.
- **Modal/Toast بدل صفحة مسار مستقل**: مرفوض — FR-008 يتطلب "وصولاً نهائياً" قابلاً
  للوصول مباشرة بالـ URL أيضاً (السيناريو 2 في US2: فتح مسار محروس مباشرة)؛ الـ modal لا
  يملك عنوان URL مستقلاً يمكن التحقق منه في اختبار.

## 7. تحقق الرول في طبقة الفاليديشن (US3 / FR-013)

**Decision**: إضافة `check('role').optional().isIn(ROLE_VALUES).withMessage(...)` إلى
`createValidate` و `updateValidate` في `Backend/utils/validation/userValidation.js`،
باستيراد `ROLE_VALUES` من `constants/roles.js`. `.optional()` لازمة لأن FR-014 يتطلب
بقاء السلوك الافتراضي (عدم إرسال `role` يعني الافتراضي القائم في المخطط) دون تغيير.

**Rationale**: هذا هو مكان الفاليديشن الوحيد المفقود المذكور صراحة في وصف المرحلة
(`userController.js:157` يأخذ `req.body.role` كما هو). إضافته هنا متسقة مع نمط المشروع
القائم بالكامل (`Backend/utils/validation/*.js` كسلاسل express-validator تُطبَّق قبل
الـ controller، كما هو موثّق في الدستور وفي كل ملفات validation الأخرى فُحصت).

**Alternatives considered**:
- **تحقق داخل الـ controller مباشرة (`if (!ROLE_VALUES.includes(req.body.role))`)**:
  مرفوض — يخالف اتفاقية المشروع الصريحة الموثّقة في الدستور: "الفاليديشن MUST يعيش في
  `Backend/utils/validation/*.js`".
- **الاعتماد فقط على `enum` مخطط Mongoose كخط دفاع وحيد (الوضع القائم)**: هذا بالتحديد
  ما تطلبه FR-013 معالجته — Mongoose يرمي خطأ عام غير مهيّأ لصيغة رد الفاليديشن
  الموحّدة في المشروع (`validatorMiddleware`)، بينما express-validator يعطي رسالة
  متسقة الشكل مع بقية الـ API.

## 8. إعادة توليد `openapi.json` (US4 / FR-015, FR-016)

**Decision**: تشغيل `npm run dump-spec` (في `Backend/`) ثم `npm run gen:types` (في
`frontend/`) كخطوة تنفيذية مباشرة — لا تعديل يدوي على أي من الملفين. `dump-spec.js` القائم
يجمع تعليقات `@swagger` من كل ملفات `routes/*.js`؛ نقصان الملف الحالي (69 عملية منشورة
مقابل ~91 معرَّفة فعلياً) سببه غياب توثيق `@swagger` كامل فوق بعض المسارات (خصوصاً
`teamRouter.js` بالكامل)، لا خطأ في أداة التوليد نفسها.

**Rationale**: السكربت والأداة (`openapi-typescript`) موجودان وقائمان بالفعل ومُستخدَمان
في تدفق العمل الموثّق في `CLAUDE.md` — لا حاجة لأداة جديدة. الفجوة سطحية (توثيق ناقص)
لا بنيوية.

**قيد تنفيذي مهم**: لو تبيّن أثناء التنفيذ أن بعض المسارات (مثل `teamRouter.js`) ينقصها
تعليق `@swagger` بالكامل، إضافة ذلك التعليق **داخل نطاق** هذه المرحلة (هي جزء من "تحديث
openapi.json" المطلوب في FR-015) — لكنها توثيق فقط، لا تغيير في المسار نفسه ولا في
`allowedTo`، فلا تخالف FR-017 (بلا تغيير سلوك مرئي).

**Alternatives considered**:
- **تحديث يدوي جزئي للملف المنشور**: مرفوض — يخالف SC-006 (تطابق 100% مع التعريفات
  الفعلية) ويُعيد إنتاج نفس مشكلة الانحراف التي أدت للفجوة الحالية.
