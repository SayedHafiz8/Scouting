# Phase 0 Research: proScout Hardening (Stage 7)

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-22

No `[NEEDS CLARIFICATION]` markers remain in the Technical Context — this file records the concrete findings that shaped the plan, each surfaced by reading the actual code rather than assumed.

## R1 — `allowedTo` role-gate denials are not logged today (the concrete gap behind FR-016/Story 5)

**Decision**: Add one call site — inside `authController.js`'s `allowedTo()` rejection branch — that invokes the existing `Backend/utils/accessLog.js` audit helper, mirroring how `middlewares/ownership.js` already logs scope-layer denials.

**Rationale**: Reading `authController.js:214-221` confirms `allowedTo` today does nothing but `next(new AppError(..., 403))` — no logging call at all. `middlewares/ownership.js` (Stage 2) already calls `logScopeDenial` on every scope-layer rejection. So "denied access attempts MUST be logged" (Constitution Principle IV) is **currently true only for one of the two denial layers** (ownership/scope), not for the coarser role gate every route also passes through. This is a real, pre-existing gap Stage 7 is the first stage positioned to close, not a hypothetical.

**Alternatives considered**:
- *Leave `allowedTo` unlogged and only assert ownership-layer logging in FR-016.* Rejected — it would make Story 5 pass by testing around the gap rather than closing it, and Principle IV names "denied access attempts" generally, not "ownership-denied attempts only."
- *Write a brand-new logging function for role-gate denials.* Rejected — `accessLog.js`'s own header comment states its reason for existing as a single call site "عشان أسماء الحقول ماتتفرقعش بين خمس مواضع نداء" (so field names don't diverge across five call sites); a second, parallel logger for the same concern reproduces exactly the fragmentation it was built to prevent.

## R2 — Distinguishing role-gate denials from scope-layer denials in the shared log

**Decision**: Extend `accessLog.js` with a second exported function, `logRoleDenial({ req, resource })`, sharing the same internal write path (same four required fields: `userId`, `role`, `path`, `resourceId`) as `logScopeDenial`, but writing `event: "role_denied"` instead of `"scope_denied"`, and deriving `resource` from the route's mount path (e.g. `req.baseUrl` stripped of the `/api/v1` prefix) rather than a domain noun, since `allowedTo` runs before any resource-specific context exists. `resourceId` is `req.params.id ?? null` — present for `/:id` routes, `null` for collection routes, matching spec.md's Edge Cases note that list-endpoint denials omit the id rather than faking one.

**Rationale**: Constitution Principle IV asks for "معرّف المستخدم، الرول، المسار، ومعرّف المورد المطلوب" (user id, role, path, requested resource id) — `allowedTo` has all four available on `req` even though it runs earlier in the chain than ownership checks. Keeping one underlying writer (not two independent `console.warn(JSON.stringify(...))` call sites) preserves the "one place, one set of field names" property the existing helper was built for; the `event` discriminator is what lets a log reader (or the FR-016 test) tell the two denial layers apart without guessing from field shape.

**Alternatives considered**:
- *Reuse `logScopeDenial` directly for role-gate denials, passing a domain-guessed `resource` string.* Rejected — it would conflate two genuinely different failure layers under one `event` value, making an incident investigator's job harder, not easier.

## R3 — Endpoint inventory format and Stage 5 baseline reconciliation

**Decision**: Reuse the exact table schema `specs/005-proscout-players-write/contracts/endpoint-inventory.md` already established — columns `Operation | Current allowedTo | proScout | Stage Δ | Enforcing layer`, disposition vocabulary `ALLOW` / `SCOPED` / `DENY` / `OPEN` — renaming only the delta column to `Stage 7 Δ` (values: `new`, `reclassified`, or `—` for unchanged), grouped by the same 11 router files (`Backend/routes/*.js`, confirmed by listing the directory: `ageGroupRouter.js`, `coachEvaluationRouter.js`, `observerEvaluationRouter.js`, `userRouter.js`, `authRouter.js`, `teamRouter.js`, `playerMediaRouter.js`, `scoutingReportRouter.js`, `playerRouter.js`, `dashboardRouter.js`, `seasonMatchRouter.js`).

**Rationale**: The Stage 5 document is already the artifact FR-003 must reconcile against; reusing its schema verbatim makes that reconciliation a row-by-row diff instead of a format-mapping exercise, and keeps the vocabulary (`ALLOW`/`SCOPED`/`DENY`/`OPEN`) consistent with what a reviewer already learned reading Stage 5's contract. `OPEN` (no `allowedTo` at all) is the disposition value that carries `GET /ages`, `GET /ages/:id`, `GET /teams`, `GET /teams/:id` — already a defined bucket in the existing vocabulary, so C-3's "documented, not closed" requirement (FR-004) fits the schema without inventing a fifth value.

**Alternatives considered**: A from-scratch inventory format — rejected per FR-003's explicit "not an unrelated, from-scratch document" requirement.

## R4 — Router-level deny-by-default guard test approach

**Decision**: The guard test (FR-012) mounts a throwaway route inside the test file itself — using the real `protect` middleware and the real Express app instance, but a route path that exists only for the duration of that test — with no `allowedTo` attached, then asserts a `proScout`-authenticated request to it is denied. This proves the *general* middleware composition behavior (any route that forgets `allowedTo` is still closed to `proScout`... except it demonstrably is **not**, since `allowedTo` is opt-in per route, not a default-deny gate by itself) — see the correction this forced in R5 below.

**Rationale / correction discovered during research**: Re-reading Constitution Principle II — "كل endpoint MUST يحمل `allowedTo(...)` صريحاً. غياب `allowedTo` يعني 'كل رول مسجّل'" (absence of `allowedTo` means "every registered role") — confirms that a route with `protect` but no `allowedTo` is **allowed to every authenticated role, including `proScout`**, not denied. So a literal "mount an unguarded route and assert 403" test would **fail by design**, because the current architecture's actual guarantee is different from what Story 4's first draft implied: there is no code-level mechanism that denies-by-default when `allowedTo` is simply omitted — that omission is a *known, accepted* residual risk the inventory (FR-002) exists to catch by human/CI-reviewed documentation, not a mechanism `allowedTo` itself provides. **This plan therefore reframes FR-012's guard test** to what is actually mechanically provable: a test asserting that `allowedTo(...)` — as a function — denies any role not in its argument list (already true and testable in isolation, independent of which routes currently use it), **plus** a second, inventory-linked check that fails CI if the number of operations in `Backend/routes/*.js` differs from the number of rows in the Stage 7 inventory (catching "someone added a route and forgot to add an inventory row," which is the actual, achievable form of "future endpoint caught by default"). This distinction is carried into `tasks.md` rather than silently implemented as originally worded, since it changes what FR-012/SC-003 can honestly claim.

**Alternatives considered**: Asserting deny-by-default is a property of the framework wiring itself (e.g., a global "reject unless explicitly allowed" middleware) — rejected as out of scope; introducing such a middleware would be a Principle II architecture change far beyond an audit stage, and risks behavior change for existing roles (Principle III) on any route whose `allowedTo` is incomplete today.

## R5 — E2E fixture for `proScout` does not exist yet

**Decision**: Extend `e2e/seed.js` to also create a `proScout` account via the same admin-API pattern already used for the coach account (idempotent create-or-skip), add `E2E_PROSCOUT_EMAIL` / `E2E_PROSCOUT_PASSWORD` to `.env.example`, and add a `loginAsProScout(page)` helper to `e2e/helpers/auth.ts` mirroring `loginAsCoach`.

**Rationale**: `e2e/seed.js` only seeds a coach today (confirmed by reading the file — it logs in as admin, then `POST /users` with `role: "coach"`, nothing else). `e2e/helpers/auth.ts` only exports `loginAsCoach`. No E2E test for `proScout` has ever existed (consistent with Stage 6's implementation note that manual/E2E browser verification for this role was explicitly skipped as out of session scope). This is a gap this stage must close to deliver Story 3/FR-013-015 at all — not an optional nicety.

**Alternatives considered**: Creating the `proScout` user inline inside the new Playwright spec via API call at test start, instead of extending `seed.js`. Rejected for consistency — `seed.js` is the established, documented, idempotent seeding entry point run once before the suite; duplicating account-creation logic inside a single spec file would diverge from the pattern every other role follows and complicate parallel test runs against the same dev DB.

## R6 — Carried-forward pitfall: fake timers and real HTTP in vitest

**Decision**: If any new test in this stage needs to control `Date` (e.g. to simulate "day of match" or token-expiry conditions), use `vi.useFakeTimers({ toFake: ['Date'] })`, never the bare `vi.useFakeTimers()`.

**Rationale**: Stage 6's implementation notes record that the default `vi.useFakeTimers()` freezes every timer, not just `Date`, which hangs any test making a real `supertest` HTTP request through Express (its internal `setTimeout`-based machinery stalls) and leaks state into subsequent tests. This stage's regression suite (FR-018) and negative tests all make real HTTP requests, so this is a live risk if any test needs date control (e.g., proving a denial is time-invariant).

**Alternatives considered**: N/A — this is a known, previously paid-for lesson being carried forward, not a new decision point.

## R7 — Discovered during implementation: `req.params`/`req.baseUrl` are stale once inspected from a captured mock argument after the response completes

**Decision**: `Backend/tests/roles/proScoutDenialLogging.test.js` spies on `console.warn` (the real sink `accessLog.js` writes to) and parses the JSON it printed, rather than mocking `logRoleDenial`/`logScopeDenial` and inspecting `req.params`/`req.baseUrl` off the captured `req` argument after `await request(app)...` resolves.

**Rationale**: Express's router restores `req.params` and `req.baseUrl` on the *same* `req` object once a layer's `next()` returns and processing unwinds past it. A `vi.fn()` spy captures a reference, not a snapshot — reading `req.params.id` from `mock.calls[0][0].req` after the HTTP response has already come back reads the *restored* (typically `{}`/`""`) state, not the state at call time. This is not a production bug: `accessLog.js`'s `writeDenialLog` reads `req.params`/`req.baseUrl` synchronously, inside the middleware's own execution, and immediately serializes to a JSON string via `console.warn` — that snapshot is correct and unaffected by the later restore. It only breaks a *test* that re-reads the live `req` reference after the fact. Spying on `console.warn` and parsing its already-serialized output sidesteps the issue entirely, and is arguably the more faithful test of "what got logged" per FR-016/Constitution Principle IV, which cares about the log entry, not the `req` object's post-hoc state.

**Alternatives considered**: Extracting only `resource` (a plain string parameter, not derived from `req` at inspection time) from a mocked spy, matching Stage 2's existing `proScoutPlayersWrite.test.js` convention — this works for `logScopeDenial` (whose caller passes `resourceId` as an already-resolved variable, e.g. `team._id`, not read from `req.params` later) but does not work for `logRoleDenial`, which derives `resourceId` from `req.params.id` *inside* `accessLog.js` itself — the caller never has a separately-resolved id to pass. Mocking `logRoleDenial` and asserting only on the (safe, string-literal) `resource` argument while dropping the `resourceId` assertion was considered and rejected as weaker coverage than the `console.warn`-spy approach, which recovers all four required fields.

## R8 — Discovered during implementation: adding `logRoleDenial` broke two existing Stage 4/5 test files (500 instead of 403)

**What happened**: Wiring `logRoleDenial` into `allowedTo()` (T031/T032) made the full Backend suite fail 30 pre-existing tests in `tests/roles/proScoutPlayersWrite.test.js` and (by the same mechanism) `tests/roles/proScoutDataScope.test.js`, every one showing `expected 500 to be 403`. Root cause: both files call `vi.mock('../../utils/accessLog.js', () => ({ logScopeDenial: fn, default: fn }))` — a factory that, before this stage, correctly listed every export the real module had. `authController.js` now imports `{ logRoleDenial }` from that same (mocked) module; since the mock factory didn't declare it, the import resolved to `undefined`, and calling `logRoleDenial(...)` inside `allowedTo()`'s rejection branch threw `TypeError: logRoleDenial is not a function` — an unhandled error that `express-async-handler` routes to `next(err)`, which `errorMiddleware.js` renders as a generic 500 (not an `AppError`), silently swallowing the intended 403.

**Decision**: Both mock factories were updated to also return `logRoleDenial: fn` (the same shared spy `fn`, matching the existing single-spy style each file already used for `logScopeDenial`). No test assertion in either file was weakened or changed — only the mock's export list was completed to match the real module's now-larger surface.

**Rationale**: This is exactly the class of regression Constitution Principle III exists to catch — a change reviewed as "additive and response-invisible" (per the plan.md Constitution Check's pre- and post-design gates) turned out to have a real blast radius once the *test doubles* elsewhere in the suite were considered, not just the production code path. The plan's Post-Design Constitution Re-Check reasoned about `allowedTo()`'s own control flow correctly (unchanged for a real invocation) but did not anticipate that other files' incomplete mocks of `accessLog.js` would turn a new import into a crash. Fixing the two mocks (not the production code) is correct: the production code is right, and the previously-incomplete mocks were a latent gap that any future export addition to `accessLog.js` — Stage 7's or otherwise — would have exposed.

**Alternatives considered**: Making the `logRoleDenial` import/call in `authController.js` defensive (e.g. `logRoleDenial?.(...)`, or a try/catch around it) — rejected. That would silently swallow a genuine wiring failure in *production* too (e.g. a typo'd export name), trading a loud, correct test failure for a silent logging gap that Constitution Principle IV explicitly does not want to be silent. Fixing the mocks is the correct fix because the mocks, not the production code, were wrong.
